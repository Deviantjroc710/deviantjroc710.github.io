A migration with no undo

Moving a decade of support history between two systems, against a date after which the old one would be gone for good.

The hard part wasn’t the volume

It was that access to the source ended on a fixed date. After it, nothing could be re-fetched — not a missed ticket, not a corrupted attachment, not a batch that looked wrong on review.

Every ordinary safety net assumes you can go back: re-pull the odd ones, run it again next week, compare later at your leisure. None of those existed here. That single constraint decided the whole design.

So everything had to be resumable

Extraction ran on cursors rather than offsets, checkpointed as it went, and could restart from where it stopped instead of from the beginning. A run that dies at hour thirty should cost thirty minutes, not thirty hours.

And checkpoints had to fail loudly

They didn’t, at first. A long run once produced nothing usable because a checkpoint was written in one shape and read back in another. Nothing raised an error — it simply resumed from nowhere and carried on looking healthy.

Checkpoints now carry a version and are validated when they are read, so a mismatch stops the run rather than silently emptying it. This is the whole of a test that can’t fail isn’t evidence, learned the expensive way: the run reported success the entire time it was doing nothing.

Then delta passes, until the gap closed

A single copy is stale the moment it finishes, because the source keeps accepting new work. So the bulk pass was followed by repeated delta passes over what had changed since the last cursor, each one smaller than the last, right up to the cutoff.

How we knew it worked

The destination was reconciled against the source while the source could still answer. Not “no errors were reported” — an actual count of what should be there against what was, run before the door closed.

Zero tickets missing. Which is the only version of this sentence worth writing down, because the alternative would have been permanent.
